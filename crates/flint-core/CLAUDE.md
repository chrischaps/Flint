# flint-core: vfs, hot reload, transform shear, the project (moved out of the root CLAUDE.md by #755)

The root file keeps the vfs rule in short. The wooze field (`flint_core::wooze`): `crates/flint-procgen/CLAUDE.md`. Quality settings (`flint_core::quality`): `crates/flint-render/CLAUDE.md`.

- **Every runtime read goes through `flint_core::vfs`** (#97) -- `vfs::read` / `read_to_string` / `read_dir` / `exists` / `is_file` / `is_dir`, never `std::fs` or `Path::exists` in a runtime crate. The default source is the disk; the web player installs a `MemorySource` filled from a game bundle (`vfs::install`; `flint bundle <game>` packs one, `flint_core::bundle` is the format, `flint-player --bundle` plays one natively, audio arrives in a late bundle and `vfs::generation()` tells the player to load it; docs/design/web.md), and tests use `vfs::scoped` (this thread only). Decode images with `flint_render::open_image` (not `image::open`) and glTF through `flint_import::import_gltf` (not `gltf::import`), both of which read via the vfs. Writes (scene save, saves, replays) and hot-reload mtime polling stay on `std::fs`, natively; input overrides go through `flint_player::user_files` (OS config dir, or `localStorage` on the web, #100), and on the web so does the `persist_*` store (`save_<game_id>.toml`, #104). Tests and the CLI keep `std::fs`
- **Hot reload never waits on the disk** (#633) -- every reload poll (scripts and `scripts/lib`, UI documents, user styles, glyph sets, palettes, style images) asks `flint_core::file_watch` (`stamp` / `modified` / `list` / `tree`), never `std::fs::metadata`. Direct mode (the default: tools, tests) stats then and there; the player's `file_watch::start()` (in `resumed`) switches to a watcher thread that publishes a change once a file held still for two 250 ms looks and was read through once; `--no-hot-reload` / `file_watch::disable()` is Off. A poll's baseline stamp must come from `file_watch` too, or the cached and direct answers never agree. Scripts read and compile on `flint-script`'s `reload_worker` thread (`engine::compiler()`, a bare engine with Flint's parse limits: keep a parser setting there, not in `ScriptEngine::new`), reading with `file_watch::read_settled`; a changed lib is compiled there into `VfsModuleResolver::with_compiled`
- **Transform shear** (#625) -- optional `transform.shear = { xz = 0.25 }` (any of `xy xz yx yz zx zy`, `ab` = how far a moves per unit of b), composed `T * R * H * S` in `Transform::to_matrix` (`flint_core::Shear`; no shear is bit-identical to before). Renderer needs nothing more: normals use `mat4_inv_transpose`, culling `transform_aabb`, both general. Rhai `set_shear(id, map)` / `get_shear` / `clear_shear`; physics warns on a skewed world matrix (`mat4_skew`) and ignores it. Demo `examples/shear_road.scene.toml` (generated by `examples/tools/shear_road.py`, `--yaw` writes the gapped before)
- **Project and manifest** (ADR 0114, #706) -- `flint_core::project::Project { root, found, id, schemas, scene, input, strict }`, over the vfs: `Project::discover(scene_or_dir)` walks up to a `flint.toml`, a `.flint/` or `schemas/` + `scenes/`|`levels/` (an engine checkout passes through to the game above), then reads `flint.toml`'s `[project]` (`id`, `schemas`, `scene`, `input`, `strict`; all optional; a wrong type or unknown key is a `ProjectError` naming file and key). `Project::current()` / `for_path(scene)` honour the CLI's global `--project <dir>` (`Project::at` + `project::set_override` in `main.rs`). A relative start is joined to the working directory only when that directory is in the file source; in a bundle it is walked as given. `flint_asset::ProjectStore` (a trait to import) adds the `.flint/` store paths. **One schema resolver** (step 2): `project::schema_dirs(scene: Option<&Path>, flags) -> Result<SchemaDirs { dirs, source }, SchemaDirsError>` is the only place the directories are decided: `--schemas` flags if any (the whole list), else the manifest's `schemas` under the root (`SchemaSource::Manifest(file)`), else discovery (`schemas/` in the working directory, beside the scene, one level up; only what exists, maybe none). A directory a flag or the manifest names that isn't there is `SchemaDirsError::Missing { dir, named_by }`; `FlintError::SchemaDirs` carries it. `flint_schema::SchemaRegistry::resolve(scene, flags) -> (registry, dirs)` builds the registry; the CLI's `common_args::load_schemas`, the viewer's `flint_viewer::app::load_schemas` (schemas + constraints of every dir, #704) and `flint-player` call it, and a new command that loads schemas must too (its `--schemas` is a `Vec<String>` with no default, so "no flags" is visible). `host_schema_dirs(listed, scene)` is a list the host settled (a bundle's manifest, `PlayerApp::set_schema_paths`): existing ones plus what's beside the scene, never an error. The player keeps a `SchemaDirs` (`set_schema_dirs`) and asks `for_scene(next)` at a transition or chunk: flags stay, a manifest is re-read for the new scene's project, discovered and host lists grow. For one release (decision 3, #765) `SchemaDirs::dropped` lists the `schemas/` near the scene that flags used to gain and no longer do (compared by `same_dir_key`), and play/render/validate/spline-edit/`flint-player` print `dropped_warnings()` on stderr; remove both with the warning. `flint-android` still builds its own two-directory list (`data_dir/engine/schemas`, `data_dir/schemas`; unbuildable here, left as it was). **Every manifest key has a reader**: `schemas` (above); `scene` is `Project::default_scene()`, what `flint play` / `flint-player` open with no scene argument (`NoDefaultScene`'s message says what to pass) and `flint bundle`'s start scene when `bundle.toml` has none; `id` is the bundle's name when `bundle.toml` has none (`commands/bundle.rs::read_project`; `flint export web` follows); `input` is the player's game input layer (`player_app/input_config.rs`); `strict` (a bool) is read by `flint_scene::diagnose`, which makes `unknown-field` an error (ADR 0115). `flint.toml` is packed into a bundle, where `Project::discover` reads it through the vfs (`tests/project_done_when_cli.rs`). `flint init` writes the manifest (#707; `crates/flint-cli/CLAUDE.md`)
- **The project root, for paths that are not searches** (`project/root.rs`, #706) -- `project.root_for(scene_dir)` is the directory a path "from the project root" is joined to: `root`, except for a `Found::Fallback` project, which keeps `guessed_root(scene_dir)`, the scene directory's parent, since with no marker the engine behaves as it did. `guessed_root` is the ONE copy of the old "scene dir's parent" guess; nothing outside `flint_core::project` may derive a root from a scene path (deriving the scene's *own* directory from its file is fine). Its callers: `load_ui` / `load_data` (`ScriptCallContext::project_root_holding`; the project arrives with `ScriptSystem::set_current_scene(path, &project)`), `music_session`'s base, the save file (`flint-player`'s `persist.rs`: `<root_for>/save/persist.toml`; #726 moves it under the OS user dir keyed on `id`, and changes that one caller), the procgen disk cache (`<root_for>/.flint/procgen-cache`) and the project-local input override (`<root_for>/.flint/input.user.toml`). What the engine writes goes under `root_for` so a `.flint/` it makes marks the root already in use. Known edge, not changed here: the nearest marker wins, so a `.flint/` beside nested scenes (an old procgen cache) is a root of its own and hides a `flint.toml` above it
- **TEMPORARY, for one release** (ADR 0114 decisions 3 and 5, #765; remove together, with a changelog entry): `SchemaDirs::dropped` / `dropped_warnings()` and the commands' `warn_dropped_schemas`; `KindInfo::old_rule` / `old_list`, `OrderChange`, `Resolution::order_change`, `list_order_changes` and the chunk-script comparison in `transition.rs`; the old-place reads `Project::old_place` / `root_holding` (a file only at `guessed_root` when that differs from `root_for`: `load_ui`, `load_data`, a music manifest), `old_persist_path` in the player's `persist.rs`, and `old_local_override` in `input_config.rs`. `guessed_root` itself stays: it is the Fallback rule
- **One asset resolver** (ADR 0114 step 3, #706; `project/assets.rs`) -- `project.resolve(AssetKind::Particles, "fire", &scene_dir) -> Result<PathBuf, NotFound { kind, name, tried }>` is the one search, over the vfs: `D/<folder>/<name><ext>` for `D` = the scene's directory, each directory above it up to and including the root, then `<root>/engine` (`engine_mount()`: only if that directory exists, never in `Found::Engine`). A kind is data, `AssetKind::info() -> &KindInfo { label, noun, folders, extensions }`, and the walk never branches on the kind: a new kind is an enum variant, a `static KindInfo` and its entry in `AssetKind::ALL` (which `flint asset where --help` and the book's table follow). A name ending in one of the kind's extensions is taken as written; a name may carry subfolders. `explain` is `resolve` with its working shown and nothing logged (`Resolution { found, tried, order_change }`, what `flint asset where` prints); `list(kind, scene_dir)` is every file visible by the same rule, a nearer name hiding a farther one (files directly in the folder only); `search_dirs` the folders in order, existing or not. Paths keep the scene directory's spelling (relative stays relative, which is what a bundle needs) and go absolute only when the spelling runs out; print them with `project::shown` (forward slashes). Two edges, the same for every kind: a scene outside the root is searched beside itself, then the root, then the engine; and a `Found::Fallback` project (no marker, root = the scene's directory) also searches one level above the scene, since with no manifest the engine behaves as it did. `Project::for_scene(scene)` is `for_path` for a loader that must carry on: a bad manifest is a warning and the project without it. TEMPORARY, for one release (decision 3, #765): `KindInfo::old_rule` is a kind's search before the one rule, as `fn(name, scene_dir) -> Option<PathBuf>`; when it would have picked another file than the one rule does (compared by `same_dir_key`; the old rule finding none is not a change), `resolve` and `list` log an `OrderChange` through `tracing::warn!` once a process per (kind, name, old, new), never on stdout. Particles' is `old_particles` (first of `particles/` beside the scene or one level up that exists, and only that folder). Remove `old_rule`, `OrderChange` and `Resolution::order_change` with the schema `dropped` warning. **Kinds on it** (`AssetKind::ALL`): `Particles`; `Models` (`models/`, `.glb` `.gltf`); `Textures` (folders `""` then `textures/`; extensions `""`, `.png`, `_color.png`; named by file); `Sprites` (`sprites/` then `""`; no extensions; named by file); `Animations` / `SpriteAnimations` / `Sequences` (all `animations/`; `.anim.toml` / `.sprite.toml` / `.sequence.toml`); `Audio` (`""` then `audio/`; `.ogg` `.wav` `.mp3` `.flac`; named by file). Three things the walk gained for them, each the same for every kind: (1) a folder of `""` is the walk's directory itself (how `audio/hit.ogg` and a loose `wall.png` are found), searched by `resolve` but never by `list`, which is of named folders only; (2) `KindInfo::named_by_file`: a name with a dot in its last part is a file name taken as written, and `Listed::name` is the whole file name (`hit.ogg`), otherwise a name is a stem; an extension of `""` is the bare name; extensions match as spelled; (3) the **as-written step**, first: a name that is a path of its own (starts `./` or `../`, or is absolute or rooted) is tried from the scene's directory with the kind's extensions, then a relative one goes through the walk and an absolute one nowhere else. `candidates(kind, name, scene_dir)` is the whole ordered list, each path once, and `tried` is its prefix. A kind loaded as a whole (the three animation kinds, the audio preload) also has TEMPORARY `KindInfo::old_list`, the files its old loader took: `list` compares the two lists (`list_order_changes` returns them unlogged), which catches a file the old search loaded and the one rule no longer reaches; kinds without it are compared name by name. The catalog and procgen stay ahead of the file search for models and textures and outside the resolver (`ModelLoadConfig::overrides`, `asked_first`). `tests/examples_asset_sweep.rs` runs every asset the engine's scenes name (100 of them under `examples/`, `tests/fixtures/` and the goldens' fixture) (and the modules their scripts import, the specs they can see, the textures their effects name) through `explain` and fails on any order change; it also prints what is found now where the old search found none. **The second group** (same PR series): `Scripts` (`scripts/`, `.rhai`, named by file, deep; an `import "m"` is the script `lib/m.rhai`; old rule `old_scripts`: the first `scripts/` that existed beside the scene or one up, and only it), `Specs` (`specs/` then `models/`, `.procgen.toml`, deep, **named inside**: old `old_spec_list`), `Prefabs` (`prefabs/`, `.prefab.toml`), `WoozePresets` (label `wooze`; `wooze/`, `.wooze.toml`), `Files` (folder `""`, no extensions: heightmap, splat map, grass mask, spline file, skybox, a scene's `input_config` and the default `config/input.toml`; `Project::file_or_beside(what, name, scene_dir)` is `resolve` for a loader that carries on: a warning with the paths tried and the path beside the scene), `ParticleTextures` (`particles/` then `""`, by file name), `Scenes` (folder `""`: a transition's target; its `old_scenes` is the one old rule that looked at the working directory, as the path as written). Two more things the walk gained, each a datum of the kind and the same for any kind that sets it: (4) `KindInfo::deep`: `list` goes into a named folder's subfolders (a folder's files, then each subfolder's, by name), a file's name carrying its subfolder (`lib/util.rhai`), which `resolve` already took; (5) `KindInfo::named_inside: Option<fn(&str) -> Option<String>>`: the kind's files state their own name (a spec's `[meta] name`, `spec_name`); `list` reads each file for it and shadows by it, `resolve`/`explain` of a plain name is the nearest listed file stating it, `tried` is the folders read (all of them on a miss, those before the find otherwise), `KindInfo::name_at(file)` is the name wherever the kind keeps it, and `candidates` does not apply. A loader that needs `tried` on a hit works from `explain` and calls `OrderChange::log()` itself (scripts keep the nearer paths to watch). In practice the scripts' and specs' *order* rarely changed (the old searches also preferred the scene's); what changed is what is **found**: a `scripts/` beside a scene hid the project's entirely, which `old_rule` finding none does not report, so the changelog says it in words. **The third group, the look and style kinds** (the last): `Palettes` (`palettes/` then `""`, `.palette.toml`), `GlyphSets` (label `glyph-sets`; `fonts/` then `""`, `.glyphs.toml`), `Fonts` (bitmap `.font.toml`; `""` then `fonts/`; its old search is the first step of the new one, so its order can't change), `FontFaces` (label `font-faces`; `fonts/`, `.ttf` `.otf` in both cases, named by file; loaded whole, old `old_font_face_list`: the one `fonts/` that existed), `Looks` (`styles/` then `""`, `.look.toml`), `Papers` / `Strokes` (`papers/` | `strokes/` then `""`; `.png` `.jpg` `.jpeg`), `Styles` (user styles; `styles/`, `.shader.toml`; loaded whole, `old_style_list`). The `""` folder is what keeps a name written as a path working (`art/dusk.palette.toml`, `--look out/tuned.look.toml`), from each directory of the walk. Their old searches are the only ones besides a transition's that looked in the **working directory** (`old_style_search`: scene, parent, cwd, spelled as nothing so a file there reads `palettes/x`); the one rule never does, and `old_rule` seeing it is what makes the warning name the file. Built-ins (palettes, looks, the `builtin` glyph set) are the loader's, after the search: `explain` knows files only, and `flint asset where` adds the built-in note. `AssetScope { project, scene_dir }` (`for_scene(path)`, `for_dir(dir)`, `new`; `resolve` / `explain` / `list` / `search_dirs` from its directory) is the handle a loader that outlives one lookup holds: the renderer (`SceneRenderer::set_asset_scope`), the style caches, debug panels. `Resolution::watched()` is what hot reload stamps: every path tried before the file found, then the file, so a nearer file that appears later is noticed. `project::same_path(a, b)` compares two spellings of one path without reading the disk. `tests/examples_asset_sweep.rs` covers these kinds too (it stands in the repo root, since their old rules read the working directory), over `examples/`, `tests/fixtures/` (the frozen scenes the goldens load, #763), the goldens' own fixture and the flags of every stylize golden. `load_ui`/`load_data`, `music_session`'s base directory, the procgen disk cache and the save file are not searches: they are paths from `Project::root_for` (next bullet but one). `SceneRenderer::load_terrain` resolves the splat map and layer textures as `Files`, and `load_chunk`'s path is one too. A new kind converts by adding its row, expressing its old search as an `old_rule`, and calling `resolve`/`list` from its loader with the host's `Project` (the player's `PlayerApp::project()`; `Project::for_scene` elsewhere); it gets a nested-scene test and a row in the book's table (concepts/assets.md)
- **Scene diagnostics** (ADR 0115 step 2, #683; `diagnostic.rs`) -- `flint_core::Diagnostic { severity, code, file, entity, component, field, message, hint }` with `Severity::{Error, Warning}` is the one shape for what is wrong with a scene; `Serialize` only (`code` is a `&'static str`). Built with `Diagnostic::error(code, msg)` / `warning` then `.file() .entity() .component() .field() .hint()`. **Codes** are the consts of `diagnostic::codes`, each with a row in `codes::ALL` (code, the severity it is raised with, meaning; a test holds the two together and the book's table in concepts/schemas.md follows it): `unknown-field` (the one warning a game meets; `promote_strict` makes it an error for `--strict` / `[project] strict`), `bad-type`, `bad-enum-value`, `out-of-range`, `missing-field`, `unknown-component`, `unknown-archetype`, `toml-parse`, `file-unreadable`, `bad-prefab`, `no-schemas`. A code never changes meaning; a new problem gets a new one. `Display` is `error[bad-type] entity 'crate' collider.friction: expected f32, got string` (no file, no hint: `one_line()` adds both, `flint validate` puts the hint on its own line). `summary_lines(scene, list, limit)` / `log_summary` (through `tracing::warn!`, `SUMMARY_LIMIT` = 5) are what a load prints: one count line, the first few with errors first, "... and N more". `closest(name, candidates)` / `did_you_mean` are the suggestion rule (same letters in another case or with `_`/`-` moved, else edit distance within a third of the name's length, 1 to 3, a swap of neighbours counting once; ties to the first by name so a HashMap's order never shows). **Who produces it**: `flint_schema::validate_component(schema, data) -> Vec<Diagnostic>` (every problem of one component table, component and dotted field set: `points[2]`, `position[1]`; missing required fields by name, then written fields by name; a schema with **no fields is open** and checks nothing, which is how a game declares a script-only component; `validate_component_data` is the old first-error `Result` over it, and `FlintError::InvalidFieldType` / `InvalidEnumValue` carry `field`), and `flint_scene::diagnose(scene_file, registry, project) -> Vec<Diagnostic>` (reads through the vfs, never stops early: unreadable file, parse error, prefab that won't expand, then `diagnose_scene(&SceneFile, file, registry)` over the expanded entities in name order: unknown archetype, unknown component, each component's fields; a `missing-field` that an archetype default or the field's own default supplies is dropped; an empty registry is one `no-schemas`, not an error per table; applies `project.strict`). **Who prints it**: every `flint_scene::load_scene` / `reload_scene` / `load_scene_string` logs the summary once and loads anyway (`load_scene_diagnosed` returns the list and logs nothing); the player's `load_chunk` does the same for a chunk; `flint validate` prints all of it and exits 1 on an error. A scene's TOML parse error names the file (`FlintError::TomlParseError("<file>: ...")`). Not here yet: entity-reference and asset checks and new field types (#684), scene-level tables (#686), the typed component view that reports through this shape (#685), `flint check` (#687), a viewer panel. Known gaps the first run over `examples/` showed: eleven engine schema files (`collider`, `rigidbody`, `character_controller`, `audio_source`, `audio_listener`, `audio_trigger`, `joint`, `parallax`, `screen_anchor`, `ui_fill`, `ui_text`) write their fields under `[component.x]` instead of `[component.x.fields]`, so they load with no fields and are open (nothing in them is checked, no schema default is applied); and a user style's `<name>_style` component has no schema of its own, so a scene that writes one needs an open schema for it (the examples' `hologram_style` is in `schemas/examples/components/`)

- **Component constants, schemas and readers agree** (ADR 0115 decision 3, #681) -- `flint_core::components` holds a name only for a component engine code uses, and `crates/flint-schema/tests/engine_schemas.rs` fails when: a constant has no `[component.<name>]` in `schemas/components/` (exempt, by name and reason, in `NO_SCHEMA`: `spline_data` and `spline_chunk`, which the engine writes and no scene authors); a constant is used by no code outside tests (`comp::NAME` / `components::NAME` under `crates/*/src`, test modules cut off), which is how `HEALTH` and `PLAYER` went; a schema is mentioned by no code outside tests, by constant or as a string literal (`NO_READER`: `audio_listener`, which nothing reads and whose file declares `active` outside a `fields` table); a room-builder name is back in the engine's set, or the root `flint.toml` stops listing `schemas/examples`; a scene or prefab anywhere in the repo writes a `model`, `light`, `spline` or `spline_mesh` value the schema rejects or a field it doesn't declare; an example (not a frozen fixture) carries a `directional_light`, `point_light` or `spot_light` table; or one of those four schemas' field lists, or which fields carry a `default`, changes without the test's list changing too. The search can't tell a reader from a writer: it catches a schema nobody mentions, not one nobody honours. A new component: the constant, the schema file with the fields its reader takes, and the reader, in one change
