### `flint_player::PlayOptions`: the web page and Android read their options as the desktop's flags do (#1142)
**What changed.** The desktop's flags, the web page's query string and Android's `dev_profile.toml` each build one `flint_player::PlayOptions` now (`PlayerArgs::options()`, `PlayOptions::from_query(&Query::parse(search))`), and one `PlayOptions::apply(&mut app)` sets the app from it: msaa, render scale, quality, styles, touch controls, frame step and seed, hold, frame rate, perf and the pass knobs. Each value goes through the same reader everywhere, so `?scale=0.5` and `--render-scale 0.5` are one setting. The desktop still refuses a value it can't read before a window opens. The page used to drop a bad `?msaa=`, `?scale=`, `?touch=`, `?fps=`, `?frame_step=`, `?seed=` or `?hold_at=` without a word. It now says each one in the console (`[flint-web] ?scale=huge: a number from 0.25 to 1, or auto`) and plays on with the default. It also checks a `?style=` word's syntax as `--style` does, and leaves out a malformed one with a warning. An unknown style name still gets through, since a user style registers later. A game binary that sets `app.launch.*` itself is unaffected. `LaunchOptions` now implements `Debug`.
**What to do.** Nothing. A Rust host that sets these launch fields by hand can build a `PlayOptions` and call `apply` instead.
